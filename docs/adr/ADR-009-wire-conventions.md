# ADR-009: Wire conventions

Status: Accepted
Date: 2026-10-03

## Context

Spec Appendix B recommends camelCase JSON externally and snake_case SQL,
while some illustrative examples in spec §7.1/§8 use snake_case keys
(`request_id`, `table_id`, `expected_seq`). The project brief's examples use
`/api/v1`, while spec §7 uses `/v1`.

## Decision

- External JSON (HTTP and WebSocket) is camelCase everywhere. The spec's
  example keys map to `requestId`, `tableId`, `expectedSeq`, `lastSeenSeq`,
  `legalActions`.
- SQL is snake_case.
- HTTP APIs are versioned under `/v1` (spec §7 is authoritative); health and
  metrics endpoints are unversioned.
- Enums are UPPERCASE strings; IDs are UUIDs (UUIDv7 generated by
  application code); timestamps are UTC RFC 3339 / `timestamptz`.
- Chip amounts are integers (int64 in Go/SQL). In TypeScript/JSON they are
  `number` constrained to the safe-integer range (±2^53−1); the ledger
  rejects amounts above `MAX_CHIP_AMOUNT` (10^15) so JSON numbers never
  lose precision.
- Error envelope: `{"error":{"code","message","requestId","details"}}`.

## Consequences

One consistent casing for all clients (web, future Unity/C#). Generated
types (TS and Go) follow the OpenAPI field names exactly.
